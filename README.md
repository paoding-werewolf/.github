# 首夜：狼人杀 AI 对战与自进化平台 — 技术文档

---

## 项目定位与核心挑战

这个项目要解决的问题是：**让 AI Agent 在信息不对称的博弈环境中自主进化**。

这带来两个相互关联的工程挑战：

1. **如何提供可信、可观测的的博弈环境**——狼人杀是信息不对称游戏，如果环境本身存在信息泄露，进化就失去了基础。编排层必须保证每个 Agent 只能看到它该看到的信息，且这种保证不能依赖代码层面的权限控制，因为共享进程、共享事件存储都可能成为开发者无意间的泄露契机。

2. **如何从高噪声对局中提取有效进化信号**——单局胜负的随机性极大，直接用胜负驱动策略修改会导致震荡。Agent 层需要一套信号处理管线，把原始对局结果转化为可信的、有因果依据的、多目标平衡的进化建议。


---

## 架构总览

系统分为两个独立部署的服务，通过 WebSocket/HTTP 通信：

**编排层**：涵盖游戏引擎、房间管理、匹配与观战。引擎持有全局视角，负责规则执行、状态流转与事件分发，是系统中唯一掌握所有角色身份和行动结果的组件。

**Agent 层**：涵盖决策、记忆与进化。每个 Agent 实例为独立进程，仅接收编排层推送的感知事件，仅返回行动决策，Agent 之间无直接通信通道。

解耦为信息创造了物理隔离：每个 Agent 只能看到编排层推送给它的内容，不存在共享记忆、共享数据库或共享网络通道。狼人 Agent 读不到预言家的查验结果，因为编排层不会把预言家的查验事件推送给狼人。信息可见性由状态机的阶段配置声明式定义，引擎按配置定向发送，各自维护单局 memory。

这种架构也带来了部署上的独立性：编排层改样式、加模块，Agent无需感知；Agent 层换 LLM、调策略，编排层不需要改，为小组内协作开发带来架构优势。

## 编排层：可信博弈环境的构建

### 声明式状态机

狼人杀的规则复杂度主要体现在阶段转移上：7 种角色、30+ 游戏阶段、警长选举+潜在的多轮pk、猎人/狼王开枪链、同守同救悖论。如果用一个大 runner 写阶段转移逻辑，在阶段数达到足够量级后将难以维护——每个阶段处理器里都要判断下一步，分支逻辑散布在各处。

我们将阶段转移抽象为纯函数：给定当前阶段和游戏状态，下一阶段唯一确定。用声明式字典替代命令式分支：

- **转移字典**：定义所有合法的阶段转移路径
- **跳过条件字典**：定义特定条件下应跳过的阶段（如守卫已死则跳过守护阶段）
- **递归解析器**：处理连续跳过的情况

状态机核心逻辑压缩到约 30 行。引擎处理各阶段的具体逻辑。由声明式配置驱动转移，修改阶段流程时只需改配置，不需要动引擎代码。

```
INIT → START_GAME → NIGHT_BEGIN
  ├→ GUARD_ACTION_BEGIN → GUARD_ACTION      [守卫守护，不能连续守同一人]
  ├→ WOLF_CHAT_BEGIN → WOLF_CHAT            [狼人私聊，串行提交+即时互播]
  ├→ WOLF_KILL_BEGIN → WOLF_KILL            [狼人击杀，多数决]
  ├→ SEER_CHECK_BEGIN → SEER_CHECK          [预言家查验]
  ├→ WITCH_ACTION_BEGIN → WITCH_ACTION      [女巫用药，一晚一瓶]
  └→ SHOOT_REMINDER                         [猎人/狼王开枪状态提醒]
       ├→ [Day1] → ELECTION_BEGIN
       │    ├→ SHERIFF_ELECTION_SIGNUP → SPEECH → VOTE
       │    ├→ [平票] → PK_SPEECH → PK_VOTE
       │    └→ ELECTION_RESULT
       └→ [其他] → DEATH_SETTLEMENT
            └→ DAWN_REPORT → SHOOT_BEGIN → SHOOT_SKILL [递归开枪链]
                 └→ SHERIFF_TRANSFER → LAST_WORDS
                      ├→ [游戏结束] → GAME_OVER
                      ├→ [夜间遗言] → DISCUSS → VOTE → ...
                      └→ [白天遗言] → NIGHT_BEGIN
```

条件转移点共 9 处，覆盖了平票 PK、开枪链递归、警长选举触发条件、遗言后分支等场景。

### 视角隔离系统

这是编排层最关键的设计决策，也是整个系统可信性的基础。

**问题本质**：狼人杀是信息不对称游戏，守卫知道守护了谁、预言家知道查验结果、狼人知道队友身份。如果引擎把所有事件广播给所有玩家，游戏直接作废。如果在每个阶段处理器里手动控制推送范围，容易遗漏且难以审计。

方案的核心思路是：编排层与 Agent 层独立部署，每个 Agent 实例为独立进程，Agent 之间无共享内存、共享数据库或直接通信通道，从通信层面消除信息泄露的可能。在此基础上，引擎为每个游戏阶段声明式地定义事件的可见范围——哪些阶段全局广播、哪些阶段仅定向推送给特定角色。这套可见性声明同时服务于三个场景：对 Agent 确保信息隔离，对观战者清晰展示每个对象的可见范围，对未来的人机对战则可直接复用为人类玩家的视角隔离。

### 玩家抽象与通信协议

引擎需要与不同类型的"玩家"交互——外部 Agent、人类玩家。通过抽象基类隔离引擎与玩家实现的耦合，引擎只持有接口字典，不关心具体是 AI 还是人。接口定义三个核心方法：感知事件推送、请求行动并等待响应、游戏开始时初始化角色与队友信息；另有可选的对局结束通知，用于触发 Agent 侧的进化管线。

三种实现覆盖不同接入方式：HTTP 接入（编排层作为客户端主动调用 Agent 暴露的端点）、WebSocket 长连接接入（支持自动重连与思考过程回调）、人类玩家 WebSocket 接入（支持断连重连与行动超时）。引擎只操作接口列表，新增玩家类型只需实现接口，引擎无需改动。

**ACT/PERCEIVE 二元协议**：Agent 仅需处理两种操作——请求行动（ACT）与感知事件（PERCEIVE）。协议将 15 种游戏阶段归一化为 Agent 可理解的动作类型，20 余种事件类型归一化为感知类型，事件记录经推导可见性、日志记录、对象构建、实时推送、落库五步完成。

### 对局管理与匹配

**板子配置**：12 人标准局（3 普狼、1 狼王、预言家、女巫、守卫、猎人、4 村民），支持随机发牌与固定角色分配。夜间死亡结算区分击杀、毒杀、悖论三种死因，按优先级与互斥关系处理。

**房间管理**：内存字典与 MySQL 双层持久化，状态流转 waiting → running → finished/aborted，支持崩溃恢复。

**匹配模式**：5 种模式覆盖不同实验需求——随机抽人、跨版本对抗、Elo 梯度匹配、循环赛、camp_evolution（同一策略不同版本在相同阵营配置下对比）。其中 camp_evolution 是编排层与 Agent 进化协同的关键桥梁，后文详述。

**观战与回放**：3D 场景渲染与 TTS 语音合成，回放数据同时作为进化管线的输入，后文详述。

## Agent 层：从高噪声对局中提取进化信号

### 进化管线全貌

Agent 层的核心贡献是一条完整的进化管线，把原始对局结果转化为可信的策略变更。管线按数据流组织：

```
原始对局结果
  → 缓冲池收集（去抖第一阶段：积累原始建议）
  → 场景聚类（去抖第二阶段：合并相似建议）
  → 双阈值确认（去抖第三阶段：快速通道 2 次一致 / 标准通道 3 次一致）
  → 因果强度加权（分离结果信号和因果信号）
  → GEPA 多目标优化（Pareto 前沿保留多样性）
  → 版本竞争（Thompson Sampling 选择最优版本）
  → 人格快照（策略版本组合变化时生成新人格描述）
```

每个环节解决一个具体问题：

**去抖**：单局胜负是高噪声信号，直接据此修改策略会导致震荡——赢了不改，输了乱改。去抖管线把策略变更的触发条件从"1 局"提升到"至少 2-3 局一致建议"，过滤掉偶然因素。

**因果强度分离**：高置信不等于高因果。一局赢了可能只是运气，直接把胜率当进化信号会引入伪进化。我们用三路分离计量：因果链分析（LLM 判断策略与结果的因果强度）× FLAG 加成（对局中实时标记 ×1.3）× 匹配度折扣（场景不匹配 ×0.7）。最终进化建议强度 = `causal_strength × flag_bonus × match_discount`。这样，一个在匹配场景下被实时标记、且 LLM 判断有因果关系的建议，其强度远高于一个不相关场景下的偶然胜利。

**GEPA 帕累托优化**：单维度优化（只看胜率）会导致策略同质化——所有策略都趋向保守求稳。GEPA（Genetic-Evolutionary Pareto Prompt Adaptation）把策略评估建模为多目标优化问题，同时考虑胜率、一致性、欺骗性、信息利用四个维度。非支配排序保留 Pareto 前沿，保证每个维度最强的个体都被保留，避免策略空间坍缩。LLM 驱动的变异与交叉生成新策略，在 Pareto 前沿的引导下探索策略空间。

**人格快照**：当策略版本组合发生变化时（全局指纹 = 当前所有策略版本的哈希快照），生成新的人格描述（名字 + 人设 + 变更日志），让策略变更对人类观察者可见。

### 记忆与 Prompt 系统

Agent 的决策质量取决于 Prompt 中注入的上下文质量。200k token 的预算不允许把所有历史信息都塞进去，需要分层存储、按需加载。

**记忆按生命周期分层**：

| 层级 | 内容 | 生命周期 | 注入方式 | 约 token 数 |
|------|------|---------|---------|------------|
| L1 工作记忆 | 当前对局的发言、投票、死亡信息 | 单局 | 直接注入 | 2000 |
| L2 对手画像 | 对手的历史行为模式 | 跨局 | 直接注入 | 1200 |
| L3 自我模型 | 自身策略偏好和已知弱点 | 跨局 | 直接注入 | 600 |
| L4 对局归档 | 完整对局记录 | 永久 | 间接（进化管线消费） | write-only |

L1 至 L3 直接注入 Prompt，L4 为 write-only 归档层，由进化管线消费后产出策略摘要间接注入，形成"归档 → 进化 → 策略注入"的闭环。

策略按粒度分层加载：索引层 → 相关全文 → 版本对比，先看索引再按需加载，避免每次都读入全部策略。

Prompt 由六个模块按固定顺序组装：批判性思维框架、对局标记提示、游戏状态、任务指令、三层记忆、进化策略注入。其中前两个为静态模块，后四个为动态模块，进化策略注入模块正是归档层间接价值的终点。整体占用约 91k/200k tokens，留有余量应对长对局。

## 跨层闭环：环境控制与进化算法的协同

### camp_evolution × GEPA

Agent 进化需要可控实验环境——相同阵营配置、相同对手，只变量是策略版本。传统匹配模式无法控制这些变量。

`camp_evolution` 匹配模式在编排层的匹配器中实现，指定同一策略的不同版本在相同阵营配置下对比。GEPA 在 Agent 层消费对比结果，计算四维适应度，驱动策略进化。编排层提供实验控制，Agent 层提供进化算法，两者通过 `camp_evolution` 模式协同。

这是整个系统"环境-进化"闭环的关键连接点：编排层保证对比的公平性（相同配置），Agent 层保证进化的方向性（Pareto 优化），回放证据链保证结果的可追溯性。

### 回放证据链

策略进化需要完整的对局 trace，不只是结果。回放数据是因果分析、FLAG 标记验证、GEPA 适应度评估的数据基础。

引擎的事件记录方法实现 5 步流水线：自动推导可见性 → 终端日志 → 事件对象构建 → 实时广播/单播 → 落库 + 房间通道推送。每一步都有明确的职责，事件对象同时服务于实时观战和事后回放。

## 技术选型

编排层后端选 FastAPI + uvicorn，主要考虑异步原生和 WebSocket 优先支持，与 Agent 层的长连接通信需求匹配。ORM 用 SQLAlchemy 2.0 的异步 session，数据库 MySQL 8.0。TTS 用 Edge TTS，免费且中文语音质量可接受。

编排层前端选 Next.js 16 + React 19，3D 渲染用 Three.js + React Three Fiber 的声明式方案，状态管理用 Zustand（轻量，适合这种中等复杂度的前端）。

Agent 层采用 Reflect + Act 双阶段决策流，每轮 2 次 LLM 调用：反思阶段分析局势、提取逻辑矛盾，行动阶段通过 Function Calling 调用 12 个角色技能工具。LLM 接入基于 OpenAI 兼容协议，当前使用 DeepSeek，可切换 Provider。进化数据持久化到 MySQL，共 5 张核心表管理技能版本、进化缓冲、策略缺口与共轭 Agent 快照。

部署用 Docker Compose，后端容器端口 8000，前端容器端口 3000，数据库 Docker 外部管理。
